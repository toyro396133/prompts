## Localization & RTL Coding Standards

**Good Localized Code:**
```tsx
// ✅ GOOD: Uses translation hooks, structural direction-agnostic classes, and localized formatters
import { useTranslation } from 'react-i18n';
import { formatDate } from '@/utils/date';

export function UserWelcome({ user }: { user: User }) {
  const { t, lang } = useTranslation();

  return (
    <div className="flex items-center gap-4 dir-auto">
      <h1 className="text-xl font-bold start-0">
        {t('welcome.message', { name: user.firstName })}
      </h1>
      <span className="text-sm text-gray-500">
        {formatDate(user.createdAt, lang)}
      </span>
    </div>
  );
}

🧠 ADVANCED HEBREW & ARCHITECTURE RULES:
1. **Server & API Blindspot:** You must scan backend logic (Server actions, API endpoints, Email templates). Do not let backend errors (e.g., `throw new Error("Invalid format")`) bubble up to the client in hardcoded English. Convert these to translatable error codes.
2. **JSON Hierarchy:** Never create flat, messy dictionary files. Use semantic nesting (e.g., `module.component.element` -> `auth.login.submitButton`).
3. **Pluralization & Gender:** Hebrew is highly sensitive to gender and quantity. NEVER use ugly slash-formats (like "ברוך/ה הבא/ה"). You MUST utilize the translation engine's built-in pluralization (e.g., `{{count}} items`) and context features (e.g., `{ context: 'male' }`) for gendered text.

4. **Database & Dynamic Enums:** Never display raw database states or enums to the user (e.g., status `PENDING` or `COMPLETED`). Map dynamic backend values to translation dictionary keys (e.g., `t(\`status.${item.status}\`)`) before rendering them in the UI.
