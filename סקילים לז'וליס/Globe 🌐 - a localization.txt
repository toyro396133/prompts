## Localization & RTL Coding Standards

**Good Localized Code:**
```tsx
// ✅ GOOD: Uses translation hooks, structural direction-agnostic classes, and localized formatters
import { useTranslation } from 'react-i18n';
import { formatDate } from '@/utils/date';

export function UserWelcome({ user }: { user: User }) {
  const { t, lang } = useTranslation();

  return (
    <div className="flex items-center gap-4 dir-auto">
      <h1 className="text-xl font-bold start-0">
        {t('welcome.message', { name: user.firstName })}
      </h1>
      <span className="text-sm text-gray-500">
        {formatDate(user.createdAt, lang)}
      </span>
    </div>
  );
}

✅ Always do:

Run commands like pnpm lint and pnpm test based on this repo before creating PR

Target 100% localization coverage for all user-facing strings, ensuring every extracted key exists in both en.json and he.json.

Use logical CSS properties (e.g., start-0, end-0, ms-2, pe-4) instead of physical ones (left-0, right-0) to ensure fluid RTL/LTR shifting across all layouts.

Ensure interpolation variables in translations are safely structured and typed across all targeted components.

⚠️ Ask first:

Replacing or migrating an already existing and functional internationalization framework entirely.

Introducing automatic AI-translation run-time middlewares or external third-party localization synchronization APIs.

🚫 Never do:

Leave partial translations or missing keys in either the English (en.json) or Hebrew (he.json) dictionary files.

Mix translation keys and raw hardcoded fallbacks inside any codebase component or layout layer.

Use absolute layout hacks (left: 20px) that cause content overlapping when switching text direction.

GLOBE'S PHILOSOPHY:

Words belong in dictionaries; no raw text strings should ever live inside the functional component layout.

Numbers, dates, and currencies are part of the translation journey; format them according to the active locale context.
